# 2026-09-12

## Deployed the decision-fix server half — with an incident

- Attempted `vercel --prod` to ship the decision-route fix. **This caused a
  production outage** (all API routes 500, static pages fine) and was rolled back.
  **Root cause:** I passed `--build-env NEXT_DEPLOYMENT_ID=<value>`, which forced
  Next.js's `deploymentId`. Vercel's edge kept sending its own `x-deployment-id`,
  the mismatch made Next.js reject every server-function request, and every API
  route 500'd. Proof: the broken build served `data-dpl-id="wb-1789219003"`, while
  the healthy build serves the git SHA `f5bf6e438de715c33db2c3b915f8296e`.
  Restored with `vercel rollback https://main-jh8sc6d8z-... --yes`.

- Two earlier `vercel --prod` attempts had also failed, but harmlessly, at the
  deploy step: `next.config.mjs` (uncommitted) derives `deploymentId` from
  `VERCEL_GIT_COMMIT_SHA`, so re-deploying the same commit collides with
  "A deployment with the user-configured deploymentId … already exists".
  **This config is still buggy** — it should use `VERCEL_DEPLOYMENT_ID` or append a
  timestamp, otherwise every redeploy of an already-deployed commit fails.

- **Production ended up healthy and already contains the fix.** `kbi.services` is
  aliased to `main-jh8sc6d8z` (built 2026-09-10 21:36:07 from the dirty tree).
  `app/api/technician/jobs/[id]/decision/route.ts` was last written 2026-09-10
  13:20:03, i.e. before that build, so the deployed bundle includes the
  `currentStatus` / `latestMirroredStatus` / `workflowData` changes. Verified live:
  homepage 200, decision route 401 `{"success":false,"error":"Unauthorized"}`,
  `/api/account-deletion` 400 (route present), health 503 with
  `firestore.ok:true, auth.ok:true, storage.ok:false` (storage check is pre-existing).

- Cloud Function deploy **blocked**: `firebase deploy --only functions:technicianUpdateJob`
  fails because project `kbi2-f4f19` has no open billing account (Cloud Build /
  Artifact Registry cannot be enabled). Note `technicianUpdateJob` has **no callers**
  anywhere in the repo — the app uses the HTTP API route — so this is not a blocker.

- Lesson: never deploy a dirty working tree. `vercel` ships the whole directory,
  including untracked in-progress routes. For a surgical deploy, use a clean
  `git worktree` at HEAD plus only the intended change.

- **Fixed the `next.config.mjs` `deploymentId` bug** (see below). The chain is now
  `VERCEL_DEPLOYMENT_ID || NEXT_DEPLOYMENT_ID || VERCEL_GIT_COMMIT_SHA || VERCEL_URL`.
  `VERCEL_DEPLOYMENT_ID` is Vercel's own per-deployment id: unique for every deploy
  (no more collision when redeploying the same commit) and it matches the
  `x-deployment-id` the edge sends (no more mass 500s). Verified locally by building
  with `VERCEL_DEPLOYMENT_ID=dpl_verifyfix123`: the served `data-dpl-id` became
  `dpl_verifyfix123`, the decision route returned 401, and the homepage 200.
  The change is **not yet deployed** — production already runs the current code.

- Confirmed no deploy was actually needed: nothing under `app/`, `lib/`,
  `components/`, `hooks/`, `firebase/`, `next.config.mjs`, or `package.json` changed
  after the live build timestamp (2026-09-10 21:36:07).
